# Synthetic desktop fixture — revision 3

This is a disposable, deterministic local development profile, never real mail. The Rust generator in `crates/fm-core/src/fixture.rs` is its source. Opening a new ordinary profile seeds it transactionally. Explicit Phase 2 live-profile initialization uses fixture revision 0 and seeds nothing; it cannot convert a demo profile. Schema 8 preserves historical synthetic revisions 1/2/3. Opening an existing profile never resets authored drafts or actions. Provider IDs intentionally collide across accounts; local identities and all commands include account scope.

Accounts: `windscribe` (synthetic Google Workspace), `personal` and `sideproject` (synthetic consumer Gmail). Each has 110 conversations, with a long 32-member thread, ordinary human mail, automated HTML-only mail, mixed read/star/category state, archived unread mail, and an explicitly missing and partial attachment. Dates are fixed to the week 2026-09-07 through 2026-09-13; fixture today is **2026-09-11**. The app must label the profile and clock as synthetic. No live provider/model connection occurs. Reading source through Core/CLI remains a query; the GUI deliberately opens a loaded snapshot with an explicit journaled read action.

## Existing protocol 1 surface (preserved in schema 5)

`Store::open(profile: &Path)` acquires an exclusive store lock. `Store::handle(method, account, params)` returns JSON or a structured `CoreError { code, message, details }`. Transport framing, client sessions and authentication belong to the engine. The store validates every account, target, revision and mutation identifier. Account is mandatory except for `accounts`, `status`, `preferences_get`, `preferences_save`, `calendar_sources` and `calendar_combined`.

| Method | Parameters | Result |
| --- | --- | --- |
| `accounts` | `{}` | `{accounts:[{id,name,email,provider,unread_count,starred_count,conversation_count,coverage}],fixture_revision}` |
| `status` | `{}` | `{schema_version,fixture_revision,revision,synthetic,fixture_today,capabilities}` |
| `conversations` | `{query?,field?:all/sender/subject/body,category?,folder?:inbox/sent/all,limit?:1..100,offset?}` | `{conversations:[{id,subject,sender_name,sender_email,snippet,latest_at,message_count,unread,starred,revision,categories,message_ids,matching_message_ids}],next_offset,coverage}` |
| `conversation` | `{id}` | `{id,subject,revision,message_ids,categories,messages:[{id,sender_name,sender_email,to,subject,sent_at,text,unread,starred,revision,source_available,attachments:[{id,name,mime_type,size,state}]}]}` |
| `flag` | `{id,message_ids:[snapshot IDs],expected_revision,request_id,read?:bool,starred?:bool}` | Updated `conversation` result. Only supplied member IDs change. |
| `draft_get` | `{conversation_id}` | `{conversation_id,body,body_html,attachment_ids,to,from,subject,revision,attachments:[metadata]}`. A nonexistent draft has revision zero. |

Never uses the network or clears the draft. |
| `calendar` | `{from?:YYYY-MM-DD,to?:YYYY-MM-DD}` | `{events:[{id,occurrence_key,calendar_id,title,start,end,time_zone,all_day,read_only,busy_only,...permitted details}],from,to,time_zone,fixture_today}`. Half-open range; at most 42 days/1,000 occurrences from at most 5,000 retained sources. |

| `view_get` | `{}` | `{account,revision,view:{}}` |
| `view_save` | `{view:{...},expected_revision,request_id}` | Same shape after saving account-scoped presentation state. |

All mutations are atomic with a durable operation response. Retrying the same account/request ID and identical command returns the original response, including after restart. Reusing that ID with changed command content returns `request_id_conflict`; an outdated expected revision returns `stale_revision`. Identifiers are opaque, bounded strings. Unknown request fields are rejected. List pages are bounded, detail threads are limited to 200 members, draft bodies to 256 KiB and view JSON to 16 KiB. The first fixture's longest thread has 32 members.

Search tokenizes Unicode alphanumeric words, treats tokens as prefix matches joined with AND, and supports sender/subject/body fields. Email punctuation divides tokens; `maya@windscribe.example` matches those address segments. Results are ordered newest first with stable ID tie-breaking, grouped into conversations, with exact matching message IDs. Raw FTS syntax is not accepted as query language. Generated summaries/drafts are never indexed. Empty query lists conversations. Binary attachments are not searched or embedded in row JSON.

Coverage counts inventory and actual FTS rows separately. Source/attachment record counts describe database metadata; aggregate retained/verified counts are `null` with verification `not_run` until an explicit full verification exists. The fixture never claims full offline completeness. Individual attachment access verifies size and hash before returning an extension-preserving export path. Intentional missing/partial content prevents claiming full offline availability. Source MIME and HTML are retained as blobs even when the reader displays decoded text. Blob bytes are staged, flushed, renamed, and only then referenced in a SQLite transaction; orphan blobs are retained safely after an interrupted seed. This is crash recovery design and test evidence, not a claim to have simulated hardware power loss.

Calendar results include only the selected account's permitted fields. Every source calendar uses the same half-open window in the response's advertised `America/Toronto` view zone; source zones still control normalization and recurrence. All-day dates remain dates. Results sort by displayed date, all-day before timed on that date, then actual timed instant and stable identity. Private/free-busy restrictions remove protected fields before JSON serialization; the fixture does not invent cross-account Busy overlay permission. The legacy `calendar` method remains account-scoped and read-only. Phase 1 exposes the bounded combined query and local fake write methods below; they enforce ACLs, scoped identities and ETags. Settings uses typed local preferences; no provider/model switches are implemented. See [calendar execution evidence](../docs/research/calendar-core-execution.md).

Schema 2 adds the local capture journal. Schema 3 transactionally adds optional authored HTML, retained draft attachment references and Google checkpoint/staging/receipt/label-intent tables. Schema 1 and 2 upgrade tests preserve existing drafts, flags, view state and captured bytes; replay does not submit again. Protocol and fixture revisions remain 1.

Omitted draft attachment IDs preserve the previous selection; `[]` clears it. Omitted HTML is preserved only if the plain body is unchanged: an older plain-text client editing the body clears the stale HTML alternative. Explicit `null` clears HTML. Save rejects cross-account, duplicate, missing and partial attachment references; capture re-verifies retained bytes. Authored plain text and HTML share the same durable Core/MIME capture path. None of these fields enables received HTML rendering or network sending.


Schema 4 adds calendar scope/ACL/checkpoint/visibility/write-receipt records and diagnostic assistance policies/results/category intents. Existing messages, authored drafts, capture receipts and per-account view state are preserved. These new fake-provider/runner entry points are Rust-internal experiments; they are not additional public IPC commands or settings controls.

Snapshot action recipes preserve the existing `flag` receipt model: deliberate open/review `{read:true}`, Done `{read:true,starred:false}`, Delay `{starred:true}`, undelay `{starred:false}`. All supply the successfully loaded conversation's `id`, `message_ids`, `expected_revision`, and `request_id`. Stale revision fails; later members are never added to the submitted snapshot. A query or restored selection cannot review mail by itself.

Per-account view allowlist also accepts `filters` containing only the typed sender/exact_sender/kind/status/has_attachment/after/before fields, `replyOpen` boolean and `selectedMember` belonging to that account. These fields never execute a provider/domain operation.

CLI additions are discoverable in `fm --help`: `mail list --grouped --sender ... --status ... --has-attachment true --after ... --before ... --cursor ...`; explicit `mail review/done/delay/undelay`; `preferences show/save`; `account-update`; `draft save --html-file ... --signature-file ... --attachment ...` or `--clear-attachments`; `draft discard/history`; `calendar --combined`; `calendar-sources`, `calendar-write --params-file ...`, `calendar-ack`, `calendar-operations`. `fm call` remains the full structured interface. Bodies, HTML, preference patches, signatures and calendar mutations accept bounded files/stdin; shell arguments are not required for authored content.

First acceptance path: fresh fixture2 profile; show saved reply thread003; deliberately open thread000 and independently read its flags through CLI; choose Done and verify both flags clear; switch account/settings and return with the saved draft intact. Full phase acceptance requires the native render/package/walkthrough evidence recorded by the integrator; this document is the boundary, not execution evidence.

## P1-08 local composition — Core 12, CLI 6, Mail UI 11

Schema **6** generalizes the existing `drafts` table; protocol **1** and fixture **2** remain unchanged. Drafts have an account-scoped durable `draft_id` and optional source conversation/member. A partial unique index retains one legacy reply per conversation, while explicit compositions have independent identities. No received conversation/message is inserted for a new draft. Migration copies every existing authored/signature/attachment/revision/discard field and leaves operation/capture journal JSON and retained bytes untouched. A legacy row's draft ID equals its former conversation ID. Current retained routing is frozen at migration; the previous schema did not store historical destinations/references, so earlier routing cannot be reconstructed. Historical creation/update timestamps remain zero rather than inventing dates.

| Method | Request | Result/meaning |
|---|---|---|
| `draft_create` | Account + `{request_id,mode,conversation_id?,source_message_id?}` | Modes `new`, `reply`, `reply_all`, `forward`. New forbids source fields; other modes require both an exact conversation and a member in that account. Returns a durable full draft at revision 1; identical request replay returns its creation receipt. |
| `draft_get` | Exactly one `{draft_id}` or `{conversation_id}` | Full draft. Conversation selector accesses its legacy reply; an absent legacy reply has revision zero and querying does not persist it. Draft-ID selector requires an existing draft in that account. |
| `draft_save` | Exactly one selector, `{body,expected_revision,request_id}`, optional `body_html`, `signature_text`, `attachment_ids`, `subject`, `to_recipients`, `cc_recipients`, `bcc_recipients`, `source_message_id` | Same atomic save/replay/conflict behavior. Optional routing fields preserve values when omitted; empty recipient arrays explicitly clear them. A first legacy save can bind the source member returned by `draft_get`; subsequent source retargeting is rejected. Account, mode and From identity cannot be changed through save. |
| `draft_discard` | Exactly one selector + `{expected_revision,request_id}` | Clears authored body, HTML, signature and attachments, preserving a revision tombstone and capture history. Discarded drafts are excluded from browsing and cannot be captured. |
| `drafts` | Account + optional `{query,limit,offset}` | `{drafts,total,draft_count,next_offset}`. Limit 1–100/default 30, offset 0–10M/default 0. Lists every persisted non-discarded draft including explicitly created empty drafts. Sort: updated_at descending, draft_id ascending. Stops a page at its count or 512 KiB summary budget; continuation uses actual returned count. `total` is filtered; `draft_count` is the full account draft total. |
| `draft_capture` | Exactly one selector + existing `{expected_revision,request_id,outcome?}` | Uses frozen recipients, subject, source context, identity/signature and authored content with the existing MIME builder and immutable capture journal. New composition needs no received source. No network or provider-sent record is created. |
| `capture_history` additions | Optional `draft_id` instead of conversation filter | Rows add `draft_id`; older legacy records infer it from conversation_id without rewriting their journal. New composition may return conversation_id null. Subject comes from the immutable new capture record. Equivalent legacy conversation/draft-ID selectors recover the same old operation/bytes without a new attempt. |

Full drafts preserve existing `from`, `from_name`, `to`, `body`, `body_html`, `signature_text`, `identity_revision`, `attachment_ids`, `attachments` and `revision`. Additions are `draft_id`, `account`, `mode`, `conversation_id` (nullable), `source_message_id`/`source_hash` (nullable), `subject`, `to_recipients`, `cc_recipients`, `bcc_recipients`, frozen `reply_to_message_id`/`references`, `reply_all_available`, `source_unavailable`, `legacy_reply`, `discarded`, `created_at` and `updated_at`. The old `to` compatibility string is the first To email or empty; expanded clients use recipient arrays. Times are Unix seconds. Draft summaries contain exactly the useful projection fields: `draft_id`, `account`, `conversation_id`, `mode`, `subject`, `body` (first 512 characters), `snippet` (first 180 characters), `to_recipients`, `updated_at` and `revision`. Accounts add `draft_count`. Per-account view state accepts folder `drafts` and a validated nullable/empty `selectedDraft` identity.

Recipients are arrays of `{email:string,name?:string|null}`, at most 100 total across To/Cc/Bcc. Email is at most 320 bytes, optional display name 4096 bytes, and routing is bounded to 64 KiB; the same address/header parser used for MIME validates saves. Subject is one line of at most 8192 bytes. Existing body/HTML 256 KiB, signature 16 KiB, at most 50 retained attachments and 25 MiB attachment bounds still apply. Empty recipients can be saved; capture requires a valid nonempty recipient set. Draft search is at most 1024 bytes/32 plain Unicode word prefixes joined with AND across subject/body/recipient text; it never searches or mutates received-source FTS. Unsupported draft filters are rejected.

Reply uses source Reply-To, otherwise From, excluding the current identity; a self-authored source falls back to its external To recipients. Reply-all includes remaining source To and Cc recipients, excludes the current identity case-insensitively, and deduplicates across recipient groups. Bcc starts empty and source Bcc is never exposed by those modes. `reply_all_available` says whether this adds visible recipients. Forward starts with an editable plain quote and `Fwd:` subject; it does not set reply headers or implicitly attach original files. Signature is displayed separately and appended once during capture.

CLI examples (select `--account` globally): `draft create`, `draft create --mode reply_all --conversation-id C --source-message-id M`, `draft list --query words`, `draft show --draft-id D`, and `draft save --draft-id D --body-file body.txt --subject "Subject" --recipients-file recipients.json`. The recipient file contains optional recipient-array keys listed above; show/save/discard/capture still accept the original positional conversation ID. Independent selectors also work with `draft history --draft-id D`. Capture remains local-only and preserves unknown-outcome recovery.

For first-save replay, the updated CLI includes the frozen source when `--expected-revision 0` is explicit. A receipt from before schema 6 may match the same first-save request with only the newly added `source_message_id` omitted, provided the old receipt has no source field. Original stored fingerprints/JSON remain unchanged; new receipts reject source changes. The capture journal has a consistent 32 KiB serialized-record bound, including the escaped 8192-byte subject. Authored Bcc is retained in private submission MIME by the existing Gmail builder and is visible only through explicit local capture inspection; Reply-all never copies source Bcc.

## P1-09 sender kinds and presentation preferences — Core 13, CLI 7, Search 5, Triage 6

Schema **7**, protocol **1**, fresh database fixture **3**. The MIME corpus remains revision 1 with identical hashes/bytes; its manifest separately names the database fixture and explicit annotations. Fresh generated human messages are people, and member 005 in each of the three accounts is automated with its retained `html-only.eml` sender, subject and recipient metadata. No runtime inference runs. `message_sender_kinds` has an account/member key, retained source hash, kind people/automated and provenance fixture. Missing/hash-stale annotations project unknown. Migrated fixture 1/2 profiles—including retained 100k fixture2 seeds—keep their revision, metadata, drafts and exact journals without annotation or reseeding.

Message-only appends update the existing bounded conversation projection; neither a completed query nor full response is cached.
