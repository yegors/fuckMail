# Synthetic desktop fixture — revision 2 (Phase 1)

This is a disposable, deterministic local development profile, never real mail. The Rust generator in `crates/fm-core/src/fixture.rs` is its source. Opening a new empty profile seeds it transactionally. Opening an existing profile never resets authored drafts or actions. Provider IDs intentionally collide across accounts; local identities and all commands include account scope.

Accounts: `windscribe` (synthetic Google Workspace), `personal` and `sideproject` (synthetic consumer Gmail). Each has 110 conversations, with a long 32-member thread, ordinary human mail, automated HTML-only mail, mixed read/star/category state, archived unread mail, and an explicitly missing and partial attachment. Dates are fixed to the week 2026-09-07 through 2026-09-13; fixture today is **2026-09-11**. The app must label the profile and clock as synthetic. No live provider/model connection occurs. Reading source through Core/CLI remains a query; the GUI deliberately opens a loaded snapshot with an explicit journaled read action.

## Existing protocol 1 surface (preserved in schema 5)

`Store::open(profile: &Path)` acquires an exclusive store lock. `Store::handle(method, account, params)` returns JSON or a structured `CoreError { code, message, details }`. Transport framing, client sessions and authentication belong to the engine. The store validates every account, target, revision and mutation identifier. Account is mandatory except for `accounts`, `status`, `preferences_get`, `preferences_save`, `calendar_sources` and `calendar_combined`.

| Method | Parameters | Result |
| --- | --- | --- |

All mutations are atomic with a durable operation response. Retrying the same account/request ID and identical command returns the original response, including after restart. Reusing that ID with changed command content returns `request_id_conflict`; an outdated expected revision returns `stale_revision`. Identifiers are opaque, bounded strings. Unknown request fields are rejected. List pages are bounded, detail threads are limited to 200 members, draft bodies to 256 KiB and view JSON to 16 KiB. The first fixture's longest thread has 32 members.

Search tokenizes Unicode alphanumeric words, treats tokens as prefix matches joined with AND, and supports sender/subject/body fields. Email punctuation divides tokens; `maya@windscribe.example` matches those address segments. Results are ordered newest first with stable ID tie-breaking, grouped into conversations, with exact matching message IDs. Raw FTS syntax is not accepted as query language. Generated summaries/drafts are never indexed. Empty query lists conversations. Binary attachments are not searched or embedded in row JSON.

Coverage counts inventory and actual FTS rows separately. Source/attachment record counts describe database metadata; aggregate retained/verified counts are `null` with verification `not_run` until an explicit full verification exists. The fixture never claims full offline completeness. Individual attachment access verifies size and hash before returning an extension-preserving export path. Intentional missing/partial content prevents claiming full offline availability. Source MIME and HTML are retained as blobs even when the reader displays decoded text. Blob bytes are staged, flushed, renamed, and only then referenced in a SQLite transaction; orphan blobs are retained safely after an interrupted seed. This is crash recovery design and test evidence, not a claim to have simulated hardware power loss.

Calendar results include only the selected account's permitted fields. Every source calendar uses the same half-open window in the response's advertised `America/Toronto` view zone; source zones still control normalization and recurrence. All-day dates remain dates. Results sort by displayed date, all-day before timed on that date, then actual timed instant and stable identity. Private/free-busy restrictions remove protected fields before JSON serialization; the fixture does not invent cross-account Busy overlay permission. The legacy `calendar` method remains account-scoped and read-only. Phase 1 exposes the bounded combined query and local fake write methods below; they enforce ACLs, scoped identities and ETags. Settings uses typed local preferences; no provider/model switches are implemented. See [calendar execution evidence](../docs/research/calendar-core-execution.md).

Schema 2 adds the local capture journal. Schema 3 transactionally adds optional authored HTML, retained draft attachment references and Google checkpoint/staging/receipt/label-intent tables. Schema 1 and 2 upgrade tests preserve existing drafts, flags, view state and captured bytes; replay does not submit again. Protocol and fixture revisions remain 1.

Omitted draft attachment IDs preserve the previous selection; `[]` clears it. Omitted HTML is preserved only if the plain body is unchanged: an older plain-text client editing the body clears the stale HTML alternative. Explicit `null` clears HTML. Save rejects cross-account, duplicate, missing and partial attachment references; capture re-verifies retained bytes. Authored plain text and HTML share the same durable Core/MIME capture path. None of these fields enables received HTML rendering or network sending.


Schema 4 adds calendar scope/ACL/checkpoint/visibility/write-receipt records and diagnostic assistance policies/results/category intents. Existing messages, authored drafts, capture receipts and per-account view state are preserved. These new fake-provider/runner entry points are Rust-internal experiments; they are not additional public IPC commands or settings controls.


## Phase 1 additive boundary — P1-00 / Core 11, Triage 5, Search 4, CLI 5

Protocol remains **1**. Schema **5** adds account metadata, typed preferences with replay receipts, and draft identity/signature snapshots. Fresh profiles seed fixture **2**: three accounts, 110 conversations each, a genuinely outgoing middle member in thread `000`, account-shaped sent members, and a saved reply in thread `003`. Calendar fixtures add editable primary sources, more overlaps/month overflow and restricted shared sources. The historical fixture-1 profile is never reseeded or expanded by migration; `status`/`accounts` report its persisted revision. Migration snapshots historical account names/signatures without changing draft body, HTML, revision, actions, captures or views.

Snapshot action recipes preserve the existing `flag` receipt model: deliberate open/review `{read:true}`, Done `{read:true,starred:false}`, Delay `{starred:true}`, undelay `{starred:false}`. All supply the successfully loaded conversation's `id`, `message_ids`, `expected_revision`, and `request_id`. Stale revision fails; later members are never added to the submitted snapshot. A query or restored selection cannot review mail by itself.

Per-account view allowlist also accepts `filters` containing only the typed sender/status/has_attachment/after/before fields, `replyOpen` boolean and `selectedMember` belonging to that account. These fields never execute a provider/domain operation.

CLI additions are discoverable in `fm --help`: `mail list --grouped --sender ... --status ... --has-attachment true --after ... --before ... --cursor ...`; explicit `mail review/done/delay/undelay`; `preferences show/save`; `account-update`; `draft save --html-file ... --signature-file ... --attachment ...` or `--clear-attachments`; `draft discard/history`; `calendar --combined`; `calendar-sources`, `calendar-write --params-file ...`, `calendar-ack`, `calendar-operations`. `fm call` remains the full structured interface. Bodies, HTML, preference patches, signatures and calendar mutations accept bounded files/stdin; shell arguments are not required for authored content.

First acceptance path: fresh fixture2 profile; show saved reply thread003; deliberately open thread000 and independently read its flags through CLI; choose Done and verify both flags clear; switch account/settings and return with the saved draft intact. Full phase acceptance requires the native render/package/walkthrough evidence recorded by the integrator; this document is the boundary, not execution evidence.
