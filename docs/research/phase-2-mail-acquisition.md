# P2-03 live mail preparation and publication

Packet: Core 15 / Gmail 5, schema 9, synthetic fixture 3 and live fixture 0. This slice supplies the shared Core boundary; engine scheduling, provider execution and live-account verification are separate. No mailbox has been accessed by these tests.

Live provider pages become durable work manifests. Bounded internal parts publish source references, normalized messages, FTS, local-intent overlays, item coverage and replay receipts atomically. An unfinished provider page can therefore have visible completed parts; its provider cursor advances only after every planned item has a durable outcome. The synthetic `GooglePageStore` keeps its whole-page behavior and existing recovery tests.

Recent, unfiltered inventory and history-delta lanes have independent checkpoints under one account mail generation. Only inventory completion counts as complete enumeration. Delta history remains authoritative while old inventory work finishes. Failed or oversized items retain explicit incomplete coverage; source retention precedes MIME parsing when decoded source bytes are available. Scan absence never deletes mail or authored drafts. Provider deletions retain local source and authored work.

MIME parsing, HTML sanitization, blob hashing, fsync and recovery hash verification run through a profile-bound preparation handle without SQLite. The Store accepts opaque prepared records and performs bounded SQL publication. Initial part ceilings are 10 items and 512 KiB serialized normalized records; these are workload bounds, not a measured 100 ms promise. Native concurrent navigation/search measurements remain required under Quality 11.

Google documents `internalDate` as epoch milliseconds determining inbox ordering; it is kept separately from the RFC Date retained in source. [Message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages). Recent priority uses a fixed epoch-seconds query cutoff to avoid the PST interpretation of date strings. [Filtering](https://developers.google.com/workspace/gmail/api/guides/filtering). Expired history requires full reconciliation and may occur before a week; no scan reset may erase retained data. [Synchronization](https://developers.google.com/workspace/gmail/api/guides/sync).

Required evidence: interrupted/replayed parts, failure visibility and incomplete coverage, off-Store preparation and recovery verification, unchanged synthetic page tests, pending authored/manual intent retention, stale generation and cross-lane updates, explicit deletion versus scan absence, and exact internalDate ordering. Results will be appended after execution.

## Implemented shared API

Core exports `google_live_mail`. Root owns schema 9 wiring and the account `connection_generation`; this module adds `mail_generation`, live lane/page/item work records, per-message coverage and incremental aggregate counters in `migration-009-mail.sql`. Existing message, FTS, attachment, category/manual-intent and synthetic checkpoint tables remain the publication destination. `PagePlan` gains serialization derives only.

1. `google_live_begin(account, baseline_history_id, recent_after_secs)` creates Recent, Inventory and Delta lanes once. The baseline must be captured before listing. The fixed recent query survives restart. Only Inventory has an unfiltered query and proves enumeration; the engine must request the agreed complete scope, including Spam/Trash. Each lane exposes its existing `Checkpoint` and a separate `complete` flag. Completed Recent/Inventory lanes park the legacy full plan's CatchUp phase; do not run another history loop from their initial baseline.
2. Call `google_live_resume_page(account, lane)` **before** requesting another provider page. An unfinished page returns its exact durable work identity and binds resumable work to the current authorized connection. If there is no pending page, use `prepare_full_page`/`prepare_history_page` and `google_live_begin_page(lane, &plan, observed_history_id)`. The observation history is the fixed full-scan baseline or the history response's top-level historyId. Beginning a Delta cycle uses the existing `Checkpoint::begin_delta` empty plan.
3. `google_live_pending(&page, limit)` returns at most 10 required IDs/actions with optional opaque staged manifests. Run `prepare_google_item(&blobs, &page, id, Some(raw_outcome), &cancel)` or `verify_staged_google_item(&blobs, &page, stored, &cancel)` on the bounded blocking preparation worker. A Delete action uses `RawOutcome::Missing`; the rare Observe-only action uses `None`. `Store::google_blob_store()` returns a cloneable profile-bound handle without SQLite. The engine must cap preparation concurrency and queued source bytes; the Core functions do not spawn workers themselves.
4. On the Store worker, call `google_live_stage_prepared(&page, &item)`, then `google_live_commit_part(&page, &[items])`. Group by both `MAX_PART_ITEMS` (10) and `MAX_PART_BYTES` (512 KiB), using `PreparedGoogleItem::normalized_bytes()`. A part has one atomic source/index/intent/coverage/receipt transaction. Exact part replay returns its previous receipt. Work from a different profile, account connection, mail generation or page is rejected. Resumed manifests require content verification again; deserialization alone cannot create a prepared proof.
5. `google_live_finish_page(&page)` advances the provider page cursor only after every requested outcome has a committed receipt. A pending provider page can already have visible completed parts. Finishing Inventory invalidates any earlier delta-current status without replacing the Delta cursor. Fresh delta catch-up must follow, including after reconnect.
6. `google_live_resync` increments the shared mail generation after expired history. It preserves all source, displayed mail, drafts, pending intent and receipts. Once enumeration ends, `google_live_reconciliation_page` selects at most 10 retained IDs absent from current observations for explicit get/404 checking. Scan absence alone neither deletes an item nor permits complete offline coverage. `google_live_gaps` paginates permanent item reasons; `google_live_retry_page` explicitly retries selected known gaps after enumeration. Permanent failures are not selected repeatedly on every poll.

`google_live_coverage` reads incremental counters and indexed cursor/receipt state without scanning the mailbox. Coverage remains available while disconnected; current/offline-complete claims require a completed delta receipt in the present connection generation. Source, text/index and attachment completeness stay distinct. A malformed decoded MIME retains its original bytes with no invented display message. Oversized HTTP/RAW responses have explicit unavailable coverage. Remote DRAFT-labeled sources are retained but remain incomplete under `remote_draft_pending` until the draft reconciliation packet owns them; they are not published as received mail or substituted for human-authored local drafts.

The live path stores signed `internal_date_ms` and uses its fixed-millisecond UTC representation for message ordering. The original RFC Date remains in exact retained MIME. The HTTP decoder accepts Google's documented signed int64 representation. Across lanes, an older provider history cannot replace newer labels or resurrect a tombstone. Failed responses without per-message metadata do not invent a message history fence from the page's global watermark. An unchanged source hash skips unnecessary FTS rewriting.

`fm-core/src/google_labels.rs` and `migration-011-labels.sql` add a per-account catalog head and generation items. The engine `google_sync/labels.rs` uses the complete `GmailCall::labels` response through the shared Gmail scheduler, with the implemented labels.list cost of one unit. Read scope and connection generation are checked before HTTP and again at each Core publication. Explicit refresh requires an active account sync job and holds a temporary operation owner. Cached queries have no HTTP path and retain separate available, connection and stale-generation indicators.

Quota admission precedes the shared RAW/preparation memory permit. That permit remains attached to downloaded labels, blocking preparation, queued Core closures and their returned results. Preparation validates, sorts and fingerprints at most 10,000 labels and 4 MiB of bounded normalized metadata off the Store writer. Stage calls carry at most 64 labels/128 KiB. Only a complete staged generation advances the visible catalog revision; abandoned/obsolete generations are cleaned in batches of at most 64 rows. A matching interrupted manifest resumes its saved offset. Concurrent manual and periodic refreshes take the expected catalog revision after memory admission, so a request waiting behind another publication does not use an earlier revision captured before that wait. A changed connection cannot replace the last published catalog with its late response.

The exact account-scoped IPC/CLI grammar and returned fields are documented in [the local protocol](../local-protocol.md#p2-07a-cached-labels-and-recovery-under-d024d025). `google_labels` pages at most 100 labels with `after` plus `expected_catalog_revision`; a changed revision requires a fresh first page. `google_category_bind` is an explicit, idempotent local command: select a present user label and either supply `create_name` for a new category or compare the existing mapping with `expected_provider_label_id` (including explicit null). Exact receipt replay survives later catalog revisions. Offline binding uses the cached catalog and a retained modification grant.
