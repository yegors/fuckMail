## Calendar interoperability

Google Calendar incremental synchronization uses sync tokens. An invalid token returns HTTP 410 and requires a new full synchronization. Keep collection scope consistent and commit the replacement cursor only after the required pages have been applied. [Calendar synchronization](https://developers.google.com/workspace/calendar/api/guides/sync)

CalDAV provides calendar access over WebDAV; iCalendar defines the event representation. WebDAV collection sync is a separate extension. CalDAV scheduling and email-delivered invitations add further protocols. Consequently, CRUD, synchronization, subscriptions, and invitation handling need separate capability tests. [CalDAV](https://www.rfc-editor.org/rfc/rfc4791), [iCalendar](https://www.rfc-editor.org/rfc/rfc5545), [collection sync](https://www.rfc-editor.org/rfc/rfc6578), [CalDAV scheduling](https://www.rfc-editor.org/rfc/rfc6638), [iMIP](https://www.rfc-editor.org/rfc/rfc6047)

Recurring series contain rules and exceptions. Google warns against updating every occurrence individually to change a series. Recommendation: preserve series identity and exceptions, expand only a bounded view window, and test occurrence/series edits independently. [Google recurring events](https://developers.google.com/workspace/calendar/api/guides/recurringevents)

Read-only URL subscriptions are a separate integration: periodically retrieve an iCalendar feed, cache a successfully parsed snapshot, and render it locally. They provide visibility, not an editable calendar or scheduling endpoint. D009 defers their implementation until after Google GUI/CLI dogfooding; editable CalDAV remains separately deferred. [iCalendar format](https://www.rfc-editor.org/rfc/rfc5545)

Calendar has per-project/per-user quotas and operational limits, including bursts of writes. Measure polling and recurrence edits with the actual project; avoid rewriting large sets of occurrences to represent a series edit. [Calendar usage limits](https://developers.google.com/workspace/calendar/api/guides/quota)

## Phase 0 scope and library feasibility

Checked 2026-09-11. OAuth is shared with the [Google investigation](gmail.md), while event permissions and recurrence remain Calendar's responsibility.

A candidate scope set is `calendar.events` for event reads/writes on accessible calendars, `calendar.calendarlist.readonly` for calendar discovery and `calendar.calendars.readonly` for calendar properties/time zones. Add `calendar.settings.readonly` only if the method inventory needs account settings. These are a proposal to verify per endpoint: owned-events-only is insufficient for writable shared calendars, and the broad `calendar` scope should not be requested merely for convenience. Calendar sharing administration is not implied. [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth)

Evaluate `icalendar` for parsing/building RFC 5545 data, `rrule` for bounded recurrence expansion and `chrono-tz` for IANA time-zone rules. The libraries cover different responsibilities. In particular, an IANA zone table does not prove support for arbitrary embedded VTIMEZONE definitions, Windows-style identifiers or preservation of unknown feed properties. Test these before adopting a representation. Record the bundled time-zone database version and how app updates refresh it. [icalendar](https://docs.rs/icalendar/latest/icalendar/), [rrule](https://docs.rs/rrule/latest/rrule/), [chrono-tz](https://docs.rs/chrono-tz/latest/chrono_tz/)

The recurrence candidate documents bounded APIs and limits that do not apply equally to unchecked/iterator paths. Bound occurrence windows and work explicitly, including sparse rules; do not expand an unending series into the database. [rrule limitations](https://docs.rs/crate/rrule/latest/source/README.md)

If the Rust shortlist cannot preserve required recurrence/time-zone behavior, compare libical on exactly the failing corpus. It is a maintained C implementation of iCalendar protocols with MPL/LGPL licensing options; an engine-side wrapper would add native build and ownership obligations. This is a contained fallback, not a reason to move calendar logic into the Qt presentation layer. [libical project](https://github.com/libical/libical)

### Scope and permission boundary

The proposed Calendar consent set is `calendar.events` for primary/shared event reads and writes, `calendar.calendarlist.readonly` for discovery, and `calendar.events.freebusy` for limited-access busy queries. `calendar.events` alone does **not** authorize `freeBusy.query`. Add `calendar.calendars.readonly` only if the endpoint inventory needs `calendars.get` beyond catalog/event metadata. Owned-only event scopes exclude writable shared calendars; broad `calendar`, settings and ACL-administration scopes are unnecessary. Request the agreed set together, verify actual grants, and gate read/write capability in the engine; do not assume installed-app incremental authorization. [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [Freebusy authorization](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query), [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).

Google now documents `writerWithoutPrivateAccess`: read/write access to nonprivate events while private events remain busy blocks. Treat this separately from writer and reader; unknown roles fail closed. Google's `owner` role means calendar manager and is distinct from the data owner. Permission filtering must precede every native/CLI projection, search, tooltip and action capability. [Sharing roles](https://developers.google.com/workspace/calendar/api/concepts/sharing), [CalendarList resource](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList).

Free/busy-only calendars need a separate bounded snapshot path, not unexpanded recurring masters or invented occurrence identities. `freeBusy.query` permits at most 50 calendars per request and 100 calendars per expanded group. Proposed pilot behavior batches explicit calendar identities, records the requested horizon and freshness, and treats per-calendar errors as unavailable coverage rather than free time. [Freebusy query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query).

### Current limits and desktop synchronization

As of **May 1, 2026**, default quotas for new projects are **10,000 requests/minute/project** and **600/minute/user/project**, over sliding windows. Projects that used the API between November 2025 and April 2026 retain prior assignments; actual Console quotas control the pilot. Google also documents a **1,000,000 requests/project/day** billing threshold and planned later-2026 charging details with advance notice. Standard use is currently available at no additional cost. Operational write limits remain separate. [Usage limits, updated 2026-09-11](https://developers.google.com/workspace/calendar/api/guides/quota).

Proposed scheduler defaults are described in the phase plan: bounded fair queues, separate Gmail/Calendar budgets, one write lane per calendar, jittered active deltas near 60 seconds and slower nonvisible work near five minutes. These are app proposals to measure against real calendar counts and quotas. Cached navigation does not wait for Google. Classify authorization/permission failures separately from retryable quota 403/429 and backend errors; use bounded backoff, jitter and applicable retry delays while retaining durable pending intent. [API errors](https://developers.google.com/workspace/calendar/api/guides/errors).

Calendar push requires a reachable HTTPS webhook with a valid certificate. Channels are resource-scoped, expire, need replacement and can overlap; notifications contain no changed resource body and may be dropped. Desktop polling fits the no-app-server boundary. The localhost OAuth callback is not a provider push endpoint. Local reminders are a separate running-app feature; their lifetime and deduplication remain engine/platform responsibilities. [Push notifications](https://developers.google.com/workspace/calendar/api/guides/push), [Reminders](https://developers.google.com/workspace/calendar/api/concepts/reminders).

### Inventory and permission freshness

Keep the original sync token through all pages of an incremental batch and publish its replacement only with a completed durable commit. HTTP 410 requires a new full provider snapshot, including after ACL-related invalidation. Stage that replacement without losing local pending intent; mark retained data stale and redact immediately when access is known denied. [Incremental synchronization](https://developers.google.com/workspace/calendar/api/guides/sync).

`events.list` can return an empty page with a continuation, and permits at most 2,500 items per page. Token deltas cannot include `iCalUID`, `orderBy`, property searches, `q`, `timeMin`, `timeMax` or `updatedMin`; other parameters stay consistent and deletions must be included. Full-detail inventory should preserve unexpanded masters/exceptions, with bounded display expansion. Unsupported rules require an explicit bounded provider-instance path or truthful unsupported coverage. [Events list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list).

**Catalog delta tokens do not establish permission freshness:** `calendarList.list(syncToken)` omits entries when only read-only properties or ACLs change. Use bounded full catalog refresh or per-calendar revalidation alongside event sync access/error information. Do not infer permission continuity or a current time zone merely from an empty catalog delta. [CalendarList list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list).

Existing code requires adaptation before full real inventory: `SyncBatch` stages at most 10,000 events in memory, the combined query rejects over 5,000 retained sources before expansion, `Access` lacks the new limited writer role, catalog names are synthetic and the display-zone path contains fixed Toronto handling. Reuse Core's source/checkpoint/journal ownership while adding durable pagination, indexed bounded projections, real catalog metadata and complete coverage semantics. These limits are synthetic app boundaries, not Google limits.

### Writes, recurrence and invitation effects

Edits/deletes use `If-Match`; a 412 must reconcile the current resource rather than overwrite it. Stable valid client-created event IDs help inspect uncertain creates but do not make a multi-request workflow atomic. `events.patch` costs three quota units and replaces supplied arrays. Google's recommended fresh get plus ETag-guarded update replaces the entire event, so preserve fields omitted by the native form, including attendees, reminders, conference and special-event data. [Conditional modification](https://developers.google.com/workspace/calendar/api/guides/version-resources), [Patch](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch), [Update](https://developers.google.com/workspace/calendar/api/v3/reference/events/update).

Preserve source IANA zones, date-only exclusive all-day ends, master identity and `originalStartTime` for moved occurrences. Retain cancelled exceptions for their parent's lifetime. Self RSVP must not overwrite other attendees; Google's `attendeesOmitted` mechanism supports participant-only response changes. [Event resource](https://developers.google.com/workspace/calendar/api/v3/reference/events).

Following edits require an update trimming the old series and an insert for the new series; Google's documented operation resets later exceptions. Keep separate instance/series/following acceptance and durable partial-progress recovery with explicit exception reconciliation. Updating every instance individually is not an acceptable series-edit implementation. [Recurring events](https://developers.google.com/workspace/calendar/api/guides/recurringevents).

Calendar writes and RSVP can send real email. Calendar alone owns attendee notifications; no second Gmail invitation is sent. `sendUpdates=none` is not a dry run: Google warns of external-calendar synchronization or event-loss problems, and some email may still be sent. Start live mutations with no-attendee events, then founder-controlled recipients; compare organizer/attendee copies and receipts. Recipient invitation settings can prevent automatic calendar appearance even after a successful API response. [Insert and notification warnings](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [Inviting attendees](https://developers.google.com/workspace/calendar/api/concepts/inviting-attendees-to-events).

Normal title/time edits must preserve existing conference data with the appropriate `conferenceDataVersion=1` semantics. Google requires a full source sync before an existing local app enables conference support, to avoid deleting stored conferences. Creating a Meet conference is a separate asynchronous operation; an editable HTTPS location field does not implement it. Keep conference Join and physical location separate. [Conference handling](https://developers.google.com/workspace/calendar/api/guides/create-events).

### Proposed real-account evidence

Use one personal Gmail and one Workspace user, with every additional intended Workspace policy/domain recorded separately. First compare primary/shared calendar reads, recurrence/DST and permission-limited details across Google web, GUI and CLI. Then exercise disposable no-attendee calendars, controlled invitations/RSVP/cancellation, remote conflicts, token recovery and following-edit interruption. Daily pilot evidence includes request counts, quota pauses, stale coverage, source/occurrence identity, reminder lifecycle and cached navigation during concurrent mail/calendar acquisition. Keep addresses, event bodies and raw responses out of committed evidence; unavailable permission/host cases remain unverified. The phase plan owns order and admission, and the Calendar contract owns resulting behavior.
