**D009 scope (2026-09-11):** Gmail and Google Calendar cover all current accounts. Retrieval and sending use Google APIs, with shared MIME parsing/building and text extraction. A small CLI grows beside the GUI; neither SMTP transport nor a received-HTML display engine is an early dependency.

## Large Gmail accounts

Gmail supports an initial retrieval followed by changes obtained through a history cursor. History can expire; an invalid cursor returns HTTP 404 and requires full synchronization. Recommendation: resumable history import plus ongoing incremental updates, with a reconciliation path that preserves local drafts and pending operations. [Gmail synchronization](https://developers.google.com/workspace/gmail/api/guides/sync)

The current documentation distinguishes new quotas effective May 1, 2026 from grandfathered project quotas. It lists 6,000 units per minute per user per project, with `messages.get` costing 20 units and `messages.list` costing 5. Illustratively, 100,000 individual gets consume 2,000,000 units: about 333 minutes (5.6 hours) at that rate, before listing, other operations, retries, or network limits. This is a quota-only lower bound for that retrieval strategy, not an import estimate or universal limit. Confirm actual quotas and any billing changes in the chosen Cloud project. [Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota)

This motivates recent-mail priority, fair scheduling across accounts, and avoiding a full metadata fetch followed by another full fetch for every historical message. The founder requires all attachments offline, so include their retrieval and quota costs in the actual import plan. Measure message count, text size, attachment size, and label membership separately; mailbox gigabytes alone are insufficient to size the work.

Gmail labels can apply to messages within threads. The local model should retain message-level labels and provider thread IDs, deriving any conversation view without multiplying message bodies for each label. [Labels](https://developers.google.com/workspace/gmail/api/guides/labels), [threads](https://developers.google.com/workspace/gmail/api/guides/threads)

The configurable-category requirement should use Gmail user labels with explicit account mappings. Gmail documents that a label applied to a thread covers existing messages but is not automatically inherited by messages subsequently added to that thread. Recommendation: retain message-level assignments and classify new arrivals independently, preserving mixed conversation membership. Label assignment and Inbox removal are separate product actions; keep read/star state independent of either. [Label behavior](https://developers.google.com/workspace/gmail/api/guides/labels)

## Google authorization and notifications

Google's installed-app flow uses the system browser and a local redirect, with PKCE available. Credentials belong in the native core. A shipped desktop application cannot keep an embedded client secret confidential. [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)

`gmail.modify` is a restricted scope covering normal read/compose/send operations without immediate permanent deletion. Public distribution and server access affect verification/assessment requirements; personal use has a documented verification exception with limits. Recommendation: validate authorization with the founder's personal and Workspace accounts early, including administrator restrictions. A local-only design does not automatically settle public-app verification. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [verification and exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)

An external OAuth project left in Testing normally receives seven-day refresh tokens for these scopes. A successful one-time login is therefore insufficient evidence of a viable daily-driver configuration. [OAuth token expiration](https://developers.google.com/identity/protocols/oauth2#expiration)

Gmail push uses Cloud Pub/Sub, and Google recommends polling-based synchronization for installed user devices. Calendar push requires a reachable HTTPS callback. The required local-only architecture points to adaptive polling while running, manual refresh, and immediate catch-up after wake/reconnect. Polling frequency and battery use must be measured. GUI close stops its polling/reminders. Under the new CLI scope, explicitly invoked headless sync/watch can operate separately; no polling continues after the final active session ends. [Gmail notifications](https://developers.google.com/workspace/gmail/api/guides/push), [Calendar notifications](https://developers.google.com/workspace/calendar/api/guides/push)

### Documented authorization facts

- A desktop OAuth client supports system-browser authorization-code flow with S256 PKCE and a random-port loopback IP callback on Windows, macOS and Linux. Installed apps cannot protect an embedded client secret. Google expressly says incremental authorization is unsupported for installed apps/devices. Revoking a grant affects all its scopes and clients in the same project for that account. [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)
- Personal Gmail plus accounts in Workspace organizations require an External audience; Internal confines the app to its organization. External Testing is limited to listed testers (100). Published-but-unverified apps have warning/user-cap consequences; verification and administrator permission are distinct. Workspace administrators can block any app. The documented Trusted override removes certain Testing constraints for the approved organization's users only. [App states](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview)
- External Testing grants with Gmail/Calendar scopes normally expire after seven days. Refresh tokens also fail after revocation, Gmail password changes, prolonged disuse, policy changes or token-count exhaustion; 100 per account/client is documented. [Token expiration](https://developers.google.com/identity/protocols/oauth2#expiration)
- Personal/known-small-group use can qualify for a verification exception, still with warning/user limits. Public distribution or moving restricted data through a server changes the verification/assessment analysis. Local-only does not itself waive all requirements. [Restricted-scope exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)
- `gmail.modify` is Restricted and supplies read, composition and send without immediate permanent deletion. `gmail.readonly` is also Restricted, so a read-only pilot does not avoid restricted-scope policy. `mail.google.com` is unnecessary for the intended feature set. [Gmail scope map](https://developers.google.com/workspace/gmail/api/auth/scopes)
- `openid email` supplies identity claims. Google says `sub` is stable, unique and never reused; email can change and must not be the identity key. Validate identity tokens/issuer/audience/expiry/nonce before linking an account. Domain text in an email is not a substitute for an actual hosted-domain claim. [OpenID identity](https://developers.google.com/identity/openid-connect/openid-connect)

**Proposed app behavior:** finalize one consent scope set for mail plus Calendar, adding `openid email` to the current three-scope feasibility set (`gmail.modify`, `calendar.events`, `calendar.calendarlist.readonly`) after Calendar's method review. Do not promise additive web-style consent. Inspect actual granted scopes; make unavailable services clear and reconnect explicitly if requirements change. Core stores a local account ID mapped to validated Google `sub`; Gmail profile and send-as discovery supply current mailbox address/capability checks, never cross-account identity by display text. One engine token coordinator serves mail/calendar and GUI/CLI, with tokens only in the OS vault. Test locked/unavailable vault, refresh races, reconnect identity mismatch and restart. Local disconnect should not silently revoke a project-wide grant used on the other computer; make revocation a separate explicit operation.

### Quotas and sending limits documented today

New Gmail project quotas effective May 1, 2026 are **6,000 units/minute/user/project** and **1,200,000/minute/project**. Projects used November 2025–April 2026 retain previous assigned quotas; inspect the chosen project. Costs: list 5; get 20; attachment get 20; history list 2; modify 5; batchModify 50; send 100; thread get 40; labels list 1; sendAs list 1; drafts list/get/create/update/delete/send 5/20/10/15/10/100. An 80M-unit daily project billing threshold is documented; current standard use has no extra charge, while later-2026 charging details remain pending with advance notice. [Gmail quotas](https://developers.google.com/workspace/gmail/api/reference/quota)

Gmail HTTP batching accepts at most 100 subrequests, recommends at most 50, charges each subrequest normally and does not guarantee execution order. [Batch semantics](https://developers.google.com/workspace/gmail/api/guides/batch)

Rate, bandwidth and concurrent-request limits are distinct; concurrency is shared by all API clients for that mailbox and has no numeric ceiling in this guide. Inspect structured error reasons, back off with jitter and honor provided retry times. Sending limits span the user's clients; 429 may persist for hours. Google cautions that delayed quota enforcement means a 200 response does not prove delivery. [Error handling](https://developers.google.com/workspace/gmail/api/guides/handle-errors)

Workspace paid accounts normally allow 2,000 messages in a rolling 24 hours; trials 500. Gmail API has 500 recipients per message; additional daily recipient constraints apply. API attachment sending is not the Enterprise Plus web-only larger allowance. [Workspace sending](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace) Personal Gmail may refuse after more than 500 messages/day or 500 recipients in a message. [Consumer limits](https://support.google.com/mail/answer/22839?hl=en)

The error guide relates API bandwidth ceilings to separate IMAP ceilings. Workspace currently lists 2,500 MB/day download and 500 MB/day upload for IMAP, and warns limits can change; these are a cross-source planning warning, not measured API-account allowances. Large attachment histories can require days even where units permit faster import. [Workspace bandwidth](https://knowledge.workspace.google.com/admin/gmail/gmail-bandwidth-limits)

**Derived example:** 100,000 individual gets ×20 units /6,000 per minute =333.3 minutes (5.56 hours) before listings, bandwidth, retries, deltas or UI reserve. This is a quota-only lower bound for that strategy, not a completion estimate. Extra attachment requests add cost if using FULL with separately retrieved parts; RAW already contains MIME, so do not assume one attachment call per part when RAW is retained.

**Proposed scheduler defaults:** cost-based buckets per project and account, a separate byte budget, and separate Gmail/Calendar service budgets beneath fair shared scheduling. Begin with 2 concurrent Gmail reads/account, 4 overall, one serialized mutation lane/account and no batching requirement. Tune only from observed actual limits. Reserve foreground read/write/delta capacity; let historical body/attachment work yield. Start at 80% of confirmed quota; an unavailable quota record uses conservative new-project values. Poll mail around 60 seconds while active, jittered, with slower idle polls and immediate wake/reconnect/manual catch-up. Treat these as adjustable proposed settings, not Google requirements. No network wait or parsing/indexing on the UI thread; cached navigation/search retain P1-10 budgets during ingestion. Never evade a per-user limit by spreading that same user's traffic across projects/accounts. No automatic billing activation or quota increase.

### Mail retrieval, retention and state

Gmail recommends polling for installed user devices; push introduces Cloud Pub/Sub. [Push guidance](https://developers.google.com/workspace/gmail/api/guides/push) Initial retrieval should cache FULL or RAW; cached label-only refreshes can use MINIMAL. History expiry returns 404 and requires reconciliation; even normally week-long history can have shorter availability. [Synchronization](https://developers.google.com/workspace/gmail/api/guides/sync)

`messages.list` returns only message/thread IDs, allows pages up to 500 and exposes an estimate rather than a coverage count. Spam/Trash requires an explicit option; `q` supports `rfc822msgid:` matching. [Message listing](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) History IDs are increasing but gapped opaque values, with a final cursor only after all pages. [History API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)

RAW is the full base64url-encoded RFC message; thread IDs and labels remain message-scoped. Reply threading requires thread ID, matching Subject and valid References/In-Reply-To. [Message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) Labels applied to a thread affect existing members; new members do not inherit them. [Label behavior](https://developers.google.com/workspace/gmail/api/guides/labels)

**Proposed integration:** reuse Core's atomic page/checkpoint/FTS/staging boundary and account-scoped remote identities. Capture an initial history baseline, publish recent source first, interleave deltas throughout full backfill and finish catch-up before claiming sync-current. Distinguish inventory scanned, source retained, attachment bytes verified, index ready and quota-paused coverage. Stage recoverable per-item failures so a large/malformed item cannot permanently poison an entire page or manufacture complete coverage. Any boundary extension needs fixtures and a Core contract revision. Never infer provider deletion from incomplete listing absence; preserve retained source, authored drafts and unresolved operations during expiry/reconciliation. Decide Spam/Trash inclusion and provider tombstone retention before full import.

Snapshot existing message IDs for read-on-open, Done and Delay; only deliberate GUI open writes read state. Prefetch, hydration and CLI queries do not. Retry journaled label changes on those exact IDs and reconcile receipts; don't use thread mutations that could accidentally include a later arrival. Category destination changes preserve unrelated labels and read/star state; Inbox removal stays explicit policy.

**Concrete current-code blocker:** `crates/fm-google/src/sync.rs` rejects decoded MIME above 40 MiB; `crates/fm-core/src/google_store.rs` rejects text above 256 KiB and more than 50 attachments, plus header bounds. Google Workspace can receive larger messages and up to 500 attachments. Revise streaming/storage/parser bounds and explicit unavailable/error behavior before arbitrary live mail; do not blindly raise all allocation caps or silently truncate retained source. [Receiving limits](https://knowledge.workspace.google.com/admin/gmail/gmail-receiving-limits-in-google-workspace)

**Proposed first-pilot policy:** local draft durability is authoritative; no keystroke waits for Google. Do not import remote draft message replacements as received conversation arrivals or mark them reviewed. Existing local captures stay historical captures; never auto-submit them when a Google account is connected.

The send journal freezes account, validated From identity, recipients, MIME bytes/hash and operation ID before one request. Transport ambiguity becomes acceptance-unknown, not automatic resend. Reconcile using returned provider IDs/history/Sent inspection and stable RFC Message-ID as evidence; an absent match does not prove no delivery and a matching ID alone does not prove deduplication. ### B1 proposal: acknowledge the provider version before comparing fidelity

Read-only review on 2026-09-13 narrows the proposed first implementation. Google documents that a draft's contained message cannot be edited after creation: replacement changes its message ID while the draft container ID stays stable. Use the message ID returned by a successful create/update acknowledgment as the version to verify. [Draft lifecycle](https://developers.google.com/workspace/gmail/api/guides/drafts), [immutable message ID and RAW representation](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages).

Retain the frozen upload MIME/hash and fetched provider RAW/hash separately. Publish a provider baseline only when the fetched draft and contained-message IDs match the acknowledgment, with the account, connection generation and operation revision still valid. Record its observation time and acknowledged local revision; newer local edits remain untouched. On later reads, a changed contained-message ID or changed RAW hash preserves the fetched version and stops automatic replacement as a conflict. Missing drafts remain distinct from proven sends. If the write acknowledgment was lost, ID-only reconciliation cannot identify which replacement was ours: retain the unknown outcome and never automatically repeat create or send.

Version identity does not prove content fidelity. Record whether the upload and provider bytes match; a mismatch remains visible and both copies stay available. Independently verify sender/recipients including Bcc, subject, threading, exact text/HTML and attachment bytes/metadata/CID in fixtures and an authorized live canary. RAW is documented as the whole message, and draft sending uses To/Cc/Bcc, but the reviewed REST documentation supplies no separate Bcc preservation guarantee or list of harmless draft rewrites. Do not silently restore missing Bcc or call a lossy parsed comparison equivalent. Explicit Send always supplies its frozen MIME. [RAW format](https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format), [draft send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/send).

This check verifies an observed version, not an atomic update precondition. Another client can edit after the preflight GET and before our PUT; a successful PUT can overwrite that unseen version, and checking our subsequent acknowledgment cannot recover it. Preserve known divergence and require explicit replacement on known conflict while disclosing this remaining race. The documented update method has no revision-precondition parameter. [Draft update](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/update).

A second strict MIME-equivalence parser is deferred: it is unnecessary for acknowledgment identity and would need separate evidence before treating transformations as harmless. Required B1 cases include changed acknowledgment/readback IDs, unchanged ID with changed RAW, local edits during readback, lost acknowledgment, and an edit between GET and PUT that demonstrates the remaining race. This is an implementation proposal only; no B1 code, tests or live draft/send capability is claimed here.
