# Phase 2 desktop authorization and native credential storage

## P2-01 boundary — 2026-09-13 UTC

Implementation starts against Platform 11, Gmail 4 and Core 14 under D020 and the [Phase 2 plan](../plans/phase-2.md). This packet owns engine-only desktop OAuth/identity verification and native credential storage. Core owns the opaque profile namespace, stable local account mapping, reconnect checks and capability publication; the HTTP packet owns bounded HTTPS transport. Existing schema 7/fresh fixture 3/protocol 1 are not changed by this packet. Deterministic **`google-p2-auth-v1`** fixtures extend the existing Google tests without live credentials or real provider requests.

The implemented boundary must bind an ephemeral IPv4 loopback listener before exposing an authorization URL; only an explicit caller opens the system browser. One-use state, S256 PKCE and nonce survive only for the bounded attempt. Code exchange verifies the signed Google ID token, issuer, client audience, time, nonce and subject before returning identity/granted scopes to Core. No ordinary query opens a browser. Tokens remain private, native-vault failures have no file/memory fallback, and each profile uses its own credential namespace. Shared account refresh must serialize across the mail/calendar consumers.

Acceptance requires deterministic success/refusal cases for callback target/state/duplicates, denial, timeout/cancel, RS256 signature/key/issuer/audience/expiry/nonce/subject, partial grants, refresh races and native-store error mapping. Tests may create and remove a uniquely named synthetic credential on the Windows host; they must never enumerate or touch existing entries. Actual Google consent, Workspace policy, long-lived refresh, physical vault locking and other-host vault behavior remain separate live gates. Test text and logs contain no real secrets or mailbox data.

Libraries are pinned with the shared transport dependency update: oauth2 5.0.0 supplies random state/PKCE, jsonwebtoken 9.3.1 verifies RSA signatures and standard JWT claims, and keyring 3.6.3 supplies explicit Windows Credential Manager, Apple Keychain and Linux encrypted Secret Service backends. Unsupported platforms must return unavailable rather than use keyring's mock default. Linux uses the synchronous encrypted Secret Service with bundled DBus; native calls run outside asynchronous transport workers. [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Google identity validation](https://developers.google.com/identity/openid-connect/openid-connect), [JWT library](https://docs.rs/jsonwebtoken/9.3.1/jsonwebtoken/), [Native keyring features](https://docs.rs/keyring/3.6.3/keyring/).

Only that newly created entry was touched; no existing credentials were enumerated. This establishes a local unlocked Windows roundtrip, not physical vault-lock behavior, other-host keyrings or Google authorization. [Native vault exercise](assets/phase-2/p2-01/native-vault.log).

Deterministic cases cover a real owned IPv4 loopback listener, wrong-state continuation, matching one-use callback and PKCE binding, denial/timeout/cancel, strict callback target/Host/duplicate/body refusal, locally signed synthetic RSA identity success and signature/key/issuer/audience/time/nonce/subject/verified-email refusal, granted-scope normalization and partial grants, missing identity/refresh/scopes and invalid token grants, explicit persistence failure, refresh subject binding, and eight concurrent consumers sharing one durably persisted refresh. The RSA private key in `google-p2-auth-v1` is an intentionally public synthetic fixture generated for these tests; it cannot authorize any provider account.

The normal explicit login requests account choice. `DesktopLogin::begin_reauthorization` additionally requests consent only for explicit missing/revoked-grant recovery; ordinary refresh never launches a browser. Google documents that offline refresh tokens must be retained and that re-consent may be necessary to replace them; this is not installed-app incremental authorization. Core receives the actual agreed-scope grant and gates capabilities. [Offline access and re-consent](https://developers.google.com/identity/openid-connect/openid-connect#refresh-tokens).

The engine must retain one coordinator per profile and cooperatively cancel/await jobs; aborting a task while a native blocking operation runs cannot stop that OS operation. Native vault calls run on Tokio's blocking pool, and a successful refresh persists rotation before reporting late cancellation. Native availability errors fail closed. No live account was connected, no real provider request was sent, and engine/GUI/CLI integration, real consent/reconnect, disk-encryption admission, account-policy denial, physical keyring locking and long-lived refresh remain unverified by this packet.

## Refresh-finalization abort handling — 2026-09-13 UTC

The asynchronous coordinator now transfers its owned account lock into the blocking vault-store finalization. Aborting the outer waiting task no longer releases that lock while the native store remains queued or running; the lock is released after the store returns, including its error path. This closes the window in which another consumer could refresh from the previous record and race a rotated credential write. The engine still cooperatively cancels and awaits jobs because an in-flight provider request or native OS call is not generally reversible.

A blocking fake vault announces its first store, pauses before changing the record, and receives an explicit release signal. The regression aborts that first waiting task, starts another consumer and verifies that it performs neither a second load nor another refresh while finalization is paused. After release, the second consumer reads the newly persisted credential, with exactly one refresh and one store. The test passed in 0.12 seconds; all **10 scoped OAuth tests** passed (the separate native-vault test stayed ignored), and strict Google-crate Clippy passed. No native credentials or provider access were used. [Abort regression](assets/phase-2/p2-01/finalization-test.log), [OAuth regression](assets/phase-2/p2-01/finalization-auth-tests.log), [Clippy](assets/phase-2/p2-01/finalization-clippy.log).

## Engine-owned login, reconnect and cancellation — 2026-09-13 UTC

The current engine runtime integrates P2-01 against Core 15/Gmail 5/Platform 11 and schema 9 under D021/D022; live fixture 0, synthetic fixture 3 and protocol 1 are preserved. Explicit begin/status/cancel/disconnect operations use the authenticated GUI/CLI session owner. Only begin returns the one-use browser URL. The runtime permits one active login, retains at most 16 terminal statuses, releases an abandoned begin reservation, closes owned loopback listeners on cancellation/shutdown, and passes only bounded presentation errors through IPC. Desktop client configuration is loaded off the Store writer from an explicit absolute path; recorded configuration paths/client IDs are references, while tokens remain exclusively in the profile-scoped vault. Mail and Calendar can share the same pooled HTTPS transport and serialized refresh coordinator.

Review identified two account-lifecycle corrections. A rejected refresh now cancels sibling provider work after durably marking that same account generation as needing reauthorization. A failure already queued behind the Core writer checks cancellation again before mutating, so a later disconnect/reconnect cannot be downgraded by stale failure. Reconnect now durably pauses an existing account before replacing its native-vault grant. The final Connected state and actual granted scopes publish only after vault persistence and an unchanged-generation check. Cancellation, process exit or a failed final Core transaction therefore leaves reauthorization required, even when the native store has already accepted the new grant. The previous stored scopes remain retained metadata while the account is paused; a cold runtime refuses provider access until explicit reconnect succeeds. New-account failure can leave an unbound vault record, which is not discoverable as a usable account and is replaced only by another verified login for that identity.

The final Windows run passes **11/11 engine authentication test groups in 2.29 seconds** and strict engine/Google all-target Clippy in **2.62 seconds**. These tests exercise actual owned loopback callbacks followed by fixture HTTPS, locally signed RSA identity verification, vault writes and real Core transactions. They cover successful identity binding, partial-grant reconnect with old job cancellation, cancellation after the native-write fixture has already changed its record, a deliberately failing final SQLite binding transaction, cold-runtime refusal and successful explicit recovery. The queued-rejection regression holds the writer, observes the queued permit, cancels account work through disconnect, then proves exactly one state-generation transition.
