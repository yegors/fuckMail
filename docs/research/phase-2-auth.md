## Refresh-finalization abort handling — 2026-09-13 UTC

The asynchronous coordinator now transfers its owned account lock into the blocking vault-store finalization. Aborting the outer waiting task no longer releases that lock while the native store remains queued or running; the lock is released after the store returns, including its error path. This closes the window in which another consumer could refresh from the previous record and race a rotated credential write. The engine still cooperatively cancels and awaits jobs because an in-flight provider request or native OS call is not generally reversible.

A blocking fake vault announces its first store, pauses before changing the record, and receives an explicit release signal. The regression aborts that first waiting task, starts another consumer and verifies that it performs neither a second load nor another refresh while finalization is paused. After release, the second consumer reads the newly persisted credential, with exactly one refresh and one store. The test passed in 0.12 seconds; all **10 scoped OAuth tests** passed (the separate native-vault test stayed ignored), and strict Google-crate Clippy passed. No native credentials or provider access were used. [Abort regression](https://github.com/yegors/fuckMail/blob/8155e998d5957e60c491475df7877553db2b453b/docs/research/assets/phase-2/p2-01/finalization-test.log), [OAuth regression](https://github.com/yegors/fuckMail/blob/8155e998d5957e60c491475df7877553db2b453b/docs/research/assets/phase-2/p2-01/finalization-auth-tests.log), [Clippy](https://github.com/yegors/fuckMail/blob/8155e998d5957e60c491475df7877553db2b453b/docs/research/assets/phase-2/p2-01/finalization-clippy.log).

## Engine-owned login, reconnect and cancellation — 2026-09-13 UTC

The current engine runtime integrates P2-01 against Core 15/Gmail 5/Platform 11 and schema 9 under D021/D022; live fixture 0, synthetic fixture 3 and protocol 1 are preserved. Explicit begin/status/cancel/disconnect operations use the authenticated GUI/CLI session owner. Only begin returns the one-use browser URL. The runtime permits one active login, retains at most 16 terminal statuses, releases an abandoned begin reservation, closes owned loopback listeners on cancellation/shutdown, and passes only bounded presentation errors through IPC. Desktop client configuration is loaded off the Store writer from an explicit absolute path; recorded configuration paths/client IDs are references, while tokens remain exclusively in the profile-scoped vault. Mail and Calendar can share the same pooled HTTPS transport and serialized refresh coordinator.

Review identified two account-lifecycle corrections. A rejected refresh now cancels sibling provider work after durably marking that same account generation as needing reauthorization. A failure already queued behind the Core writer checks cancellation again before mutating, so a later disconnect/reconnect cannot be downgraded by stale failure. Reconnect now durably pauses an existing account before replacing its native-vault grant. The final Connected state and actual granted scopes publish only after vault persistence and an unchanged-generation check. Cancellation, process exit or a failed final Core transaction therefore leaves reauthorization required, even when the native store has already accepted the new grant. The previous stored scopes remain retained metadata while the account is paused; a cold runtime refuses provider access until explicit reconnect succeeds. New-account failure can leave an unbound vault record, which is not discoverable as a usable account and is replaced only by another verified login for that identity.

## D034 account lifecycle assessment — 2026-09-13 UTC

**Historical proposal before D036; implementation and current scoped evidence are recorded above.** The following assessment describes source as it stood after schema-16 B3B, when removal/restore was absent and paired addition acceptance remained pending. D034 required account addition and removal through both native and CLI interfaces, and distinguished removal from disconnect, local-data deletion and OAuth revocation. This assessment itself changed no contract or runtime boundary and authorized no real account action; its references to required decisions and implementation gaps are historical.

Current source provides much of account addition. `check_google_connection` and `bind_google_account_with_client` in [live_profile.rs](../../crates/fm-core/src/live_profile.rs) validate the verified Google subject, preserve stable account identity across reconnects, and enforce the profile's desktop-client identity. [GoogleBackend.cpp](../../gui/GoogleBackend.cpp), [SettingsView.qml](../../gui/SettingsView.qml) and the [CLI](../../crates/fm-cli/src/main.rs) expose explicit login/reconnect/disconnect. Addition still needs its paired native/CLI acceptance; existing source and earlier OAuth fixture passes do not prove that entire workflow.

Removal is absent. `google_disconnect` in [google_auth.rs](../../crates/fm-engine/src/google_auth.rs) cancels account work and advances durable connection state/generation, retaining both credentials and content. `NativeCredentialVault::remove` in [vault.rs](../../crates/fm-google/src/vault.rs) can delete the exact profile/account credential, including an already-absent entry, but it is not part of `CredentialVault` or the shared [TokenCoordinator](../../crates/fm-google/src/auth.rs). A removal implementation must serialize cleanup with refresh and verified-grant finalization using that same owned account lock; the native vault's per-call lock alone cannot prevent a later refresh store from recreating a credential.

The smallest proposed policy is explicit removal from active Mail/Calendar navigation, deletion of the local credential, and retention of cached data, unsent work and all uncertain receipts in a discoverable read-only removed-account area. This would differ from disconnect without silently purging data. Google-side revocation and permanent local-data cleanup remain separate choices. Whether this retained-data policy is sufficient for the founder's removal workflow must be settled before coding.

Proposed implementation reuses the existing Store: retain the account/provider identity and foreign-key parents, add a separate active/removed lifecycle plus bounded pending-cleanup metadata, and reuse `operations` for immutable completed receipts. A revision-bound preview/removal/status boundary would expose local removal and credential cleanup separately. Commit inactivity and a new connection generation before off-writer cleanup. Vault failure or process exit leaves the account inactive with explicit pending cleanup; it must not report successful credential deletion. Exact late provider outcomes still reach their original journals, while old generations cannot claim new writes or publish source changes. Known-unsent and unknown work remain distinct, with no removal-induced retry or fabricated outcome.

Lifecycle checks would need both public dispatch and direct Core/off-writer finish paths: [Store dispatch](../../crates/fm-core/src/lib.rs) currently checks account existence, and [accounts()](../../crates/fm-core/src/queries.rs) lists every account. Existing immutable request replay should remain first. Combined Calendar defaults must exclude removed accounts. [MailBackend::loadAccounts](../../gui/MailBackend.cpp) only selects a replacement when the current account ID is empty, so removing the selected or last account needs explicit handling, dirty-draft preservation and invalidation of late callbacks. Retained drafts, source history, attachments and receipts must remain reachable through their exact identities.

Restoration should require explicit OAuth for the same verified subject and reattach retained data, rather than create a duplicate or let ordinary Add silently reactivate it. Pending credential cleanup must be fenced against a new grant. Sign-in alone must not resume retained outbound work. Do not remove the user-selected OAuth configuration file: it is a shared client reference. The disposition of the profile's single-client-ID restriction after all accounts are removed also needs an explicit choice.

Minimum proposed tests are two-account and last-account removal; dirty GUI input and concurrent CLI saves; exact replay/conflicting IDs; held refresh/store versus cleanup; locked vault, cancellation and crash before/after each durable boundary; restart discovery of pending cleanup and retained work; prepared/in-flight/unknown/late-accepted Send, draft and Calendar receipts; exact retained RAW/attachment exports; same-subject restore and different-subject refusal; stale-generation publication refusal; and zero Google deletion/revocation requests. Addition tests should cover native/CLI cancellation, duplicate identity, partial grants and restart without implicit import. No new tests, builds, performance runs or account actions were performed for this assessment.

### Historical first-slice implementation seams

A further read-only review during P2-06B confirms that the existing single-client-ID restriction can remain unchanged when all accounts are removed. This preserves current behavior and avoids making client replacement part of removal. The retained-archive preference question remains unanswered; the proposed policy below is not a founder answer or authorization to remove any real account.

The proposed shared commands are revision-bound `account_remove_preview`, `account_remove`, `account_remove_status` and explicit `google_auth_restore_begin`, with existing authentication status/cancellation reused. A separate lifecycle revision prevents connection-state changes from silently authorizing removal; an explicit `retention:"archive"` request names its effect. Keep at most one pending credential cleanup per account and retain terminal request receipts in `operations`. Exact replay may resume that same cleanup, while restoration requires its completion and the same verified Google subject. Neither restoration nor sign-in resumes retained outbound work or starts sync. Explicit-account read queries and revision-bound exports can serve the archive, but deliberate archive opens must suppress read-on-open mutations. Active/default account and combined Calendar queries exclude removed accounts. Shared guards must cover local-content begin/finish and provider claim/publication, while preserving prior receipt replay and late outcome recording. Local off-writer plans also retain the monotonic lifecycle revision: removal followed by restoration cannot revive an old autosave or copy proof merely because the account is active again. Prepared-operation replay may return retained status in the archive but cannot resume provider work. Native account removal must separately retain an unsaved buffer with its original account/draft identity and fence late save callbacks; such a buffer is not relabeled as saved archive content or attached to a fallback account.

The existing engine auth test harness already exercises real owned loopback callbacks, signed synthetic identity grants, mutable fixture credentials and held store finalization. Paired addition/restoration needs a separate default-off fixture that begins without bound accounts and retains these production listener/PKCE/state/nonce paths. The current acquisition fixture prebinds accounts, refuses vault writes and disables login, so it cannot establish account addition. A scoped native test URL handler and isolated CLI browser-launch seam can complete controlled callbacks without opening a real browser; the fixture report must omit codes, tokens and authorization URLs. Independent account/subject/generation, callback closure, cancellation, partial-grant, wrong-subject and zero-import assertions are required. This is a seam assessment only: no fixture, RPC, schema or removal implementation was added here.
