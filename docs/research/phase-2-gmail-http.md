# P2-03 / P2-05 — explicit Gmail HTTP calls

Started 2026-09-13 UTC under the authorized Phase 2 goal, Gmail 4 / Core 14 / Platform 11 / Quality 11, unchanged fresh fixture 3. Core's separate live boundary now uses schema 8 / live fixture 0. This slice adds account-bound HTTP call builders and typed responses; it does not import real accounts, run a sync worker, alter source storage or submit a message.

Before code, acceptance is: fake HTTP transport tests verify method/path/query/body encoding, exact account/method quota identity, page tokens and bounded responses; RAW missing/oversized/malformed per-item outcomes; history-only 404 expiry; explicit message-ID mutations; stable draft IDs independent of replaced message IDs; sanitized errors; and a single uncertain-send result after loss/malformed receipt/server failure. Existing replay plans and journal-before-send remain the integration owners.

Official method documentation and current costs checked on 2026-09-13: [quota method table](https://developers.google.com/workspace/gmail/api/reference/quota), [profile](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile), [message list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [history](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list), [message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages), [draft replacement](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/update), [draft behavior](https://developers.google.com/workspace/gmail/api/guides/drafts), [send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send). Costs are method units, not one unit per HTTP request; actual project/account allowances still come from Console. These endpoints do not document an exactly-once send key or draft revision compare-and-swap.

The builder uses the approved Gmail HTTPS base and URL-encodes every ID/query parameter. The worker supplies a matching account token after quota admission. It must persist mutation intent/InFlight before executing, consume RAW outcomes into explicit coverage, preserve local/remote draft versions and reconcile ambiguous writes. No generic retry, batching, permanent deletion, alias administration, HTML renderer or MIME parser is introduced here.

## Implemented API and consumer obligations

`fm_google::gmail_api` exposes `GmailCall` builders, `GmailMethod::quota_units`, account-bound `GmailApi<T: HttpTransport>` and `GmailReply`. Each call supplies its immutable account/service/class/unit identity through `work()`. Reads can explicitly choose UserRead/DeltaRead/BackfillRead; callers cannot relabel a mutation as a retryable read. The worker enqueues that metadata, obtains a matching account access token and calls `execute(call, access_token, cancel)` once after admission. A different call account is rejected before transport.

There are 15 concrete methods: profile, message list/history/RAW, labels, single-message modify/trash/restore, draft list/get/create/update/delete and direct/draft send. Query and path encoding preserve opaque page tokens and IDs; invalid page limits, controls and dot-only path segments fail before HTTP. Message state methods operate on an explicit existing ID and verify the returned message identity. No thread mutation or permanently deleting a received message exists in this adapter.

Existing `sync::ListPage`, `HistoryPage` and `RawMessage` remain the replay boundary. `RawOutcome` separates Available/Missing/TooLarge/Malformed; Available retains the existing RAW message plus `internalDate`/`sizeEstimate` as `RawItem`. The adapter validates base64url encoding in bounded chunks, while MIME decoding/parsing and persistence stay in their existing owners. The **40 MiB received MIME ceiling remains explicit**; an oversized item must create an incomplete-coverage record, never silently disappear or prevent every other item from progressing. Full larger-source retention/streaming and the existing Core attachment/parser bounds remain unresolved for arbitrary live mail. Normal metadata responses are capped at 4 MiB; RAW/draft-get JSON caps include base64 expansion and fixed overhead. Authored submissions are capped at 35,000,000 MIME bytes; composition validation and recipient/From decisions precede these builders.

`GmailDraft.id` remains separate from its replaceable `message.id`. RAW draft get retains complete authored source. Create/update provide frozen MIME and optional thread ID, with no invented If-Match/CAS promise. Draft send includes frozen MIME in the documented Draft body; known remote conflicts and explicit replacement consent remain the engine's responsibility. [Draft send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/send) accepts a Draft resource; the guide describes updated-content submission. An accepted reply retains the new provider message/thread IDs, not the old draft-content identity.

`GmailReply::Submission(GmailSubmission)` separates `result: send::SubmissionResult` from `error: Option<GoogleError>`. A valid successful receipt is Accepted, explicit client/auth/quota rejection is Rejected, and transport failure/cancel, 5xx or malformed successful receipt is NoDefinitiveResponse. The optional sanitized error preserves 401 reauthorization, 403 policy versus quota classification, 429 Retry-After and 5xx/transport failures for worker status/cooldowns. An Accepted reply has no error. No call is repeated, including when its error would be retryable for reads. Core must persist frozen MIME/account/recipients and InFlight before `execute`, then persist/reconcile `result` and handle `error` separately; a successful API receipt is not proof of delivery. This adapter does not bypass or replace the existing journal-before-send model.
