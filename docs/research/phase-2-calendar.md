# Phase 2 Google Calendar adapter

## P2-04 / P2-06 boundary — 2026-09-13 UTC

This packet consumes Calendar 12, Core 14, Platform 11 and D020's [Phase 2 plan](../plans/phase-2.md). `fm-calendar` will add an account-bound HTTP adapter over P2-02's bounded transport, with **`google-p2-calendar-v1`** deterministic fixtures. Existing recurrence, edit plans and synthetic fixture 1 stay compatible. No database, engine, UI or schema ownership moves into the adapter.

The adapter owns exact Calendar catalog/event/free-busy methods, scoped URL encoding, safe failure classification and full provider-source retention. Core owns durable page staging, token publication, permission freshness/redaction, capability checks, operation journaling and reconciliation. The shared scheduler owns quotas and retries. Methods submit once and never connect an account or launch a browser.

Catalog pages include hidden/deleted entries and require a page cursor or final sync cursor, including empty intermediate pages. Catalog deltas omit ACL-only/read-only metadata changes, so the engine must separately revalidate the catalog or individual entries. Detail-event sync retains unexpanded masters/exceptions with unchanged query parameters; no time window or search parameter is exposed on the token path. A 410 is an explicit replacement signal and cannot erase cached data inside this adapter. [Catalog list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list), [Event list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list).

Free-busy queries use at most 50 explicit calendars and a bounded displayed window. Per-calendar errors/missing responses are unavailable coverage, never free time; no event or occurrence identity is invented. Event writes require explicit caller authorization and durable intent, ETag preconditions where applicable, deliberate notification policy and preserved conference/attachment semantics; no method retries an uncertain write. [Free-busy query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query), [Event patch](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch).

Acceptance is deterministic method/URL/query/pagination, full-versus-delta query equality, 410/412/permission/rate/cancel failure, role/private-data handling, bounded free-busy coverage and provider-field/ETag preservation. Live Google, real permission propagation, Workspace policies, engine durable staging and notification delivery remain separate gates.

Pages retain unknown provider fields, recurrence, conference/attachment metadata, time zones, role and default reminders. The fixed app defaults are 250 entries per catalog/event page, a 16 MiB page-response bound, 2 MiB individual event/write body bound, and a validated existing 42-day displayed window for free-busy. These are application limits, not Google service limits. Oversized or malformed pages fail explicitly; Core still needs durable failure/coverage reporting and staged publication before unrestricted inventory. Multi-page cycle detection across restarts belongs to Core; this adapter rejects an immediate repeated page token.

`CalendarRole::event_access(private)` retains limited-writer behavior for a resolved event. Persist the distinct `writerWithoutPrivateAccess` role and apply private master/exception inheritance before projecting or editing. An entire limited-writer calendar must never be mapped to legacy `Access::Writer`; until integrated role-aware expansion exists, a conservative reader projection is safe. Catalog deltas alone do not prove permission freshness. Raw adapter sources are private engine inputs and must not be sent directly to GUI/CLI projections.

Patch sends `If-Match`, the reviewed `sendUpdates` value, `conferenceDataVersion=1` and `supportsAttachments=true`. Omitted fields retain Google's patch semantics; replaced arrays must come from complete source. Core must refuse attendee writes from truncated/`attendeesOmitted` input, gate new conference creation separately, and retain authored work on conflict. Google currently charges **3 quota units for events.patch**; cost that method separately from the other one-request primitives. `sendUpdates=none` is not a dry run. [Patch semantics and costs](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch).

These results verify request construction and domain regressions only. Engine durable staging/indexed queries, permission-loss redaction across all views, real provider quotas/cadence, new limited-writer projections, controlled Google writes/notifications, reminders and live personal/Workspace acceptance remain unverified by this packet.

## P2-04 engine read acquisition and recovery — 2026-09-13 UTC

The native worker now consumes Core 15 / Calendar 13 under D022, schema 9, live fixture 0 and preserved synthetic fixture 3. `google_sync/calendar.rs` uses the engine's shared quota-aware HTTP facade and checked Core writer admission. It completes/resumes the catalog, separately refreshes known calendar metadata/permissions, and gives each permitted calendar one durable event page per pass. Immediate backfill continuations skip already-complete calendars; ordinary refresh passes perform deltas. Event sources remain unpublished until their complete run seals. A broken individual calendar response is reported without hiding another calendar's completed data. Free/busy requests acquire only an explicitly requested displayed window, at most 50 calendars per request, and preserve per-calendar unavailable outcomes.

Integration exposed and corrected recovery gaps in the existing Core API. Catalog checkpoints are available only to native workers. Pending source consolidation is discovered through bounded indexed candidates after restart, including published or expired runs. A saved staging run can be rebound only to the current verified account connection with unchanged checkpoint/permission state; old responses retain the old lease and are refused. Permission observations still advance their ordering fence. When the effective role and zone are unchanged, matching staging runs carry forward without restarting a large calendar. A changed role or zone durably clears the old event token and marks coverage incomplete until fresh inventory succeeds, preventing an ACL upgrade from leaving previously restricted sources permanently incomplete. Catalog/free-busy-only grants can refresh metadata without acquiring ungranted event-detail access.

An expired catalog/event token causes one explicit full replacement attempt while preserving the prior committed view. A partially staged provider page that changes when re-fetched is expired and cleaned up before replacement; mixed responses are never published. Source acquisition and cursor advancement remain separate bounded writer calls, with cancellation/connection checks on each admission. No remote mutation is implemented or submitted by this worker.

The final integrated Windows/Rust 1.88.0 run passes **36 Core Calendar tests and 6 engine worker tests**; target tests have no ignores. Core tests finish in 16.25 seconds and the six engine groups in 0.26 seconds; these are test runtimes, not navigation benchmarks. Strict all-target Clippy for Core and engine passes. ## P2-04 off-writer preparation and bounded SQL — 2026-09-13 UTC

D023/Core 16/Calendar 14 refines the preceding worker without changing its publication pointers, page receipts or fixture identities. The preparation changes add no SQL schema; the concurrently implemented state/write journals advance the shared store to schema 10. Live fixture 0, synthetic fixture 3 and protocol 1 are preserved. The native engine now acquires the shared two-page memory permit after quota admission and retains it through HTTP decoding, blocking preparation and queued Core publication. Resumed catalog finalization acquires the same memory budget without another HTTP charge.

`prepare_calendar_page` creates an opaque page from provider values outside the writer. It canonicalizes each observed item, computes its receipt hash and streams the compatible page manifest once per fetched page. Core mints a bounded prior-source input; `prepare_calendar_chunk` merges sparse cancellations and reuses the existing event normalizer off-writer, retaining only canonical source and compact index fields for SQL. The normalizer's own per-event serialization/256 KiB domain check is unchanged. Prepared Store calls recheck the profile, exact connection/run, permission/base/projection context, manifest and prior-source generation stamps. A stale sparse base requires fresh preparation from current Core state; the fetched page is not hashed again. Catalog receipt verification, finalization metadata extraction and individual metadata-response serialization also move off-writer. Synchronous fixture compatibility entry points remain available.

Ordinary preparation input contains at most 32 items and 1 MiB of observed plus selected prior bytes, with the existing single-large-item exception. A fetched page retains the 16 MiB limit. Core checks a prior source's SQL byte length before copying it and rejects more than 32 MiB. A sparse merge is assembled off-writer from bounded inputs, then a capped serializer refuses a result beyond 32 MiB before normalization. These are logical source-byte limits, not a physical allocation or RSS measurement; existing domain-validation limits remain distinct. `calendar_preparation_limit` preserves old source and continuation instead of sealing the page. Consolidation now chooses at most 32 IDs within a 1 MiB SQL source/observed-byte target, with a single-large-item exception, without copying their JSON into Rust. Existing SQLite indexing triggers still parse JSON during actual SQL writes.

## P2-06 first live write slice — 2026-09-13 UTC

D023/Core 16/Calendar 14 and shared schema 10 add native Core/engine execution for explicit no-attendee create/edit/delete and dedicated self-RSVP. The existing `calendar_write_operations` journal gains a local/live mode fence, execution state/revision, attempt, connection/permission generations, frozen dispatch and provider-outcome fields. Synthetic commands and receipts keep their existing behavior. Live fixture 0, synthetic fixture 3 and protocol 1 remain unchanged. The engine exposes this slice through root-owned Google Calendar write/reconcile/operation routing; these methods do not make the complete Calendar or Phase 2 milestone ready.

Fresh catalog permission and complete event reads precede a durable `ready` stage. Ready is known not dispatched, survives restart/cancellation, and may be revalidated only by another explicit execution of the same immutable request. The worker releases read data and its memory seat before waiting for mutation quota. After quota and response-memory admission, Core rechecks the exact connection, permission epoch and source revision and claims `in_flight` immediately before one provider request. Restart converts only in-flight live attempts to `unknown`; reconciliation performs reads and never replays a mutation. A typed quota cooldown learned after the claim proves no HTTP was dispatched, so its exact attempt returns to ready with preserved intent; late evidence cannot revert a newer attempt or accepted receipt. A shared memory permit accompanies queued Core payloads and replies so canceled callers cannot release capacity while those values remain queued.

The slice permits ordinary, unlocked, nonrecurring organizer copies with no attendees for CRUD. Self-RSVP requires writable access to the authenticated attendee's copy and uses only that attendee's response plus `attendeesOmitted:true`. Omitted fields remain omitted; unchanged conference links are accepted as form input without rewriting conference data. New conference creation/changes, attendee-list changes, recurrence, special event types and timed/all-day conversion are explicitly unsupported here. Google documents the participant-response flag and the required attendee-calendar write access. [Event fields](https://developers.google.com/workspace/calendar/api/v3/reference/events), [attendee RSVP](https://developers.google.com/workspace/calendar/api/concepts/inviting-attendees-to-events).

Creates freeze a base32hex-compatible event ID derived from scoped operation identity. Edit/delete retain the reviewed ETag; 412 becomes a retained conflict. Interrupted/malformed responses remain unknown, and duplicate create IDs require read reconciliation. Provider success is durably recorded independently of current connection or cache revision. Same-base older staged reads can be expired and consolidated in bounded chunks before publication; a newer published event or changed authority is preserved while the receipt remains available. A missing resource alone cannot prove successful deletion. PATCH consumes three quota units and replaces supplied arrays; this slice records `sendUpdates=all` and never treats suppressed notifications as a dry run. [Conditional requests](https://developers.google.com/workspace/calendar/api/guides/version-resources), [PATCH semantics](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch), [error distinctions](https://developers.google.com/workspace/calendar/api/guides/errors).
