## Goal and boundaries

Reduce durable database growth and improve cold/search/list latency as accounts grow, while retaining exact offline source bytes, authored drafts, user flags, provider coverage, recovery and uncertain-write receipts. GUI and CLI continue to share one engine command/query boundary. Existing [Core](../contracts/core-storage.md), [Gmail](../contracts/gmail.md), [Calendar](../contracts/calendar.md), [Search](../contracts/search.md) and [Quality](../contracts/quality.md) contracts govern behavior until a reviewed decision updates them.

The founder has chosen a fresh local database with no old-profile migration or preservation. Accounts will be re-authorized and re-synced. Use disposable generated profiles for design and verification; switch the real profile only when the replacement build and recovery/package checks are ready. New profiles still need to preserve their own authored drafts, exact source bytes, manual choices and uncertain provider receipts going forward.

## Decisions for review

1. **Reset boundary — accepted by D091:** create an intentionally incompatible fresh schema at a version **above every schema version shipped or in progress at integration** (at least 32 after D090 added schema 31). Do not reset `user_version` to 1: older executables only refuse higher versions and could mistake a version-1 database for an old migratable profile. A new engine should reject every pre-reset version with a clear fresh-start instruction instead of applying the historical chain. Remove the old chain from fresh runtime creation, preserve its history/evidence in Git, and keep a small versioned migration runner for changes after the new baseline.
2. **Current profile disposition — accepted by D091:** discard current local data at cutover; no draft/settings/receipt migration or export is required. Re-authorize and re-sync accounts. Stage the profile switch after the new build is verified so ongoing app work is not interrupted by a half-built schema. OS-vault credentials and application registration are separate from SQLite.
3. **Space and latency tradeoff:** use the existing [quality workload](../contracts/quality.md#representative-workload) and budgets; do not invent a new pass threshold or equate database shrinkage with faster painted navigation. Preserve `synchronous=FULL` unless a separate durability decision changes it.
4. **Derived representation:** choose whether internally compact integer keys, normalized millisecond timestamps, a persisted conversation summary, external-content FTS and typed workflow columns earn their added write/recovery complexity after the measurements below. Public account/message/thread IDs and protocol 1 should remain stable unless the owning contracts are deliberately revised.

### 0. Planner correction with focused evidence

- Treat the confirmed account-scoped FTS join order as a standalone near-term fix. On a disposable profile, run `PRAGMA optimize=0x10002` when the long-lived Store opens and `PRAGMA optimize` periodically or at close; check the actual search plan, exact results and warm/cold timing. The follow-up audit found an FTS-first plan and large improvement after planner statistics on an in-memory profile copy. Keep this packet independent of the full generated-corpus work in A.
- Preserve the current query if statistics choose a good plan. Force FTS-first join order only if generated rare/common terms, account filters and concurrent writes still demonstrate a slower plan. A plan assertion must use the bundled SQLite build and a known corpus; recheck after SQLite upgrades.

### A. Reproducible baseline before changing storage

- Extend the existing generated corpus with varied thread lengths, body sizes, progressively repeated quoted reply chains, labels, Calendar recurrence/cancellations, drafts, incomplete sources and two-account overlap. Measure retained full MIME/blob bytes separately from the new-contribution SQLite/FTS projection; existing pre-D088 rows were not backfilled. Keep all generated databases/logs in ignored local or CI artifact storage. Record current source and executable identities, SQLite build/version, host, database/WAL/blob sizes and `dbstat` by table/index.
- Measure cold and warm search, filtered and grouped conversation pages, review/flag updates, recipient suggestions, Calendar range/mail-count queries, bounded sync writes and engine queue wait. Record p50/p95/p99, `EXPLAIN QUERY PLAN`, memory and checkpoint behavior, with and without concurrent ingestion. Include the pre/post planner-correction result. Compare the current real-profile plan using metadata only; do not benchmark or mutate private mail content.
- Establish a correct result oracle for every comparison: account scope, exact matching members, folder/count totals, source and FTS coverage, and page continuity. The current 100k warm-search and 20k query results remain historical evidence, not measurements of the proposed schema.

### B. Bounded improvements that do not require a reset

- Add a category-first index and an active provider-date range index only after showing the target queries and their write/space cost. Keep `messages_conversation` until real plans and before/after measurements show it is unnecessary. Review exact-sender matching and other-account recipient suggestions as query changes; a `LIMIT` after a global sort does not bound sorting work.
- Split **journal compaction** into large payload rows and smaller proof headers. A completed Gmail page can have no pending items yet its item rows still provide exact `google_live_commit_part` receipts on replay; retain or replace that proof before deleting them. Calendar item/page rows may be pruned only after publication and source consolidation, with the run header still available for generation-based coverage and exact publication replay. Keep all incomplete, uncertain and otherwise referenced work. Make each handoff and prune transactionally restartable, then test crashes at each boundary, repeated part/page calls, full inventory/catch-up and honest coverage across two accounts. Publication alone is not a deletion rule.
- Inventory `operations`, mail mutation, capture, Calendar-write and preference receipts separately. Do not age out a terminal row merely because its state is confirmed: reused request IDs must not repeat an external action or lose exact replay. Consider compact tombstones or a bounded retention window only with an explicitly revised replay contract and durable duplicate fence. Unresolved and uncertain records remain until reconciled.
- Measure reclaimed pages and file size after compaction. Choose explicit, bounded reclamation only if needed; WAL size settings do not delete journal rows, and incremental auto-vacuum is not automatic row retention policy.

### C. Fresh schema candidate, only after the reset boundary is accepted

- Replace the version-2 create-and-upgrade path with one reviewed current-schema transaction at the post-D090 baseline version chosen above. Use `STRICT` tables where values/types fit; run `foreign_key_check` and verify old engines refuse the new version. Do not carry all historical migration code into normal fresh creation. Preserve exact immutable receipts and the shared GUI/CLI wire identities.
- Compare internal integer account/conversation/message keys or compact binary hashes against current long text keys using realistic multi-account data. Keep unique external IDs and account-scoped ownership constraints. Add selective foreign-key cascades for genuinely dependent rows **after** account-removal and unknown-work guards; do not turn account deletion into an unchecked single statement.
- Store normalized UTC instants as integers for filtering/ordering while retaining the original provider/header date when needed for provenance and display. Design `(account,time,id)` and conversation/member indexes from actual query plans, including Calendar mail counts. Verify offset dates, DST civil-day boundaries, stable cursor order and older/synthetic date inputs.
- Make `messages` a narrow metadata table only if measurement warrants the additional join. Compare ordinary FTS, the isolated contentless-delete candidate and an external-content index over one derived reading-text table; retain exact MIME/HTML/attachment bytes in the verified blob store. Also measure FTS5 `detail=column` and prefix-index choices against the application's current token-prefix/column-filter queries, Unicode tokenizer boundaries and possible future phrase queries. Do not adopt a smaller index from SQLite's example size alone. Define atomic insert/update/delete, source-version changes, rebuild, index-coverage counting and account purge. Search must never silently report unindexed rows as complete. Evaluate whether the existing quote-trimmed derived text reduces the benefit before choosing the design.
- Maintain a bounded conversation summary only if the measured full-account scan remains material. The row must cover latest order, review/hold counts, folder membership and chosen sender kind, and change in the same transaction as message/flag/kind changes. Verify arrival, move, Trash, provider deletion, manual overrides, rollback and restart against an independent message-level oracle. Use keyset paging for ordered list queries where it preserves the present cursor semantics; do not sacrifice exact filtered totals without a contract decision. Retire the in-memory conversation projection only after parity; assess first-page, search-generation and coverage caches separately because the summary does not replace their distinct correctness and performance roles.
- Move frequently filtered draft/send state, provider target and due time out of JSON expressions into typed indexed columns. Keep exact JSON receipts/history where replay requires them. Compare index count, database size and write amplification before removing any existing expression index.
- Preserve Calendar's distinct raw-observation and normalized/merged-source semantics. If most observations are equal, store a nullable observed override or an equivalent reversible form; prove sparse cancellations, recurring exceptions, limited permissions and rebuild retain exact behavior. The follow-up audit found repeated model settings occupying most snapshot bytes; compare a content-addressed immutable settings table referenced by hash while retaining exact source/settings stale-result and manual-precedence checks. Do not assume the sparse `local_model_settings_history` is a complete reference store.
- Consider explicit account/blob references and hash-directory sharding if account purge or file-count evidence warrants them. Retain cross-account deduplication and exact-byte verification; cleanup cannot infer blob ownership by scanning arbitrary text fields.

### D. Optional concurrency and tuning after measured need

- Keep one writer and short, bounded transactions. Add a read-only engine connection only if queue-wait evidence shows benefit after query/projection changes. Define snapshot revision, invalidation, cancellation and maximum read lifetime; deliberate open still commits its read receipt through the writer. GUI and CLI must not bypass Core authorization or consume an inconsistent blend of snapshots.
- Measure cache size, memory mapping, temporary storage, checkpoint cadence, WAL residual size and page reclamation separately on all supported hosts. Do not enable every pragma by default. Long readers must not pin WAL indefinitely. Keep `synchronous=FULL` for authored content and uncertain provider receipts until an explicit alternative durability policy is accepted.

## Acceptance and rollback gates

- **Correctness:** seeded two-account GUI/CLI agreement; independent SQL or fixture oracles for list/search/counts; no cross-account result; exact FTS/source/attachment coverage; draft and unknown-send replay; Calendar catalog/recurrence/invitation and partial-permission recovery; account remove/restore/delete with other-account preservation; `foreign_key_check` and FTS rebuild after interrupted work.
- **Scale:** run the [100k rapid, 1m primary and 3m stress tiers](../contracts/quality.md#representative-workload), with varied content and the roughly 25 GB/100 GB scenarios when feasible. Report cold/warm p50/p95/p99, engine queue and native input-to-paint separately, ingestion throughput, memory, database/index/WAL/blob size and restart/rebuild time. A synthetic index-density pass cannot establish full offline-content readiness.
- **Durability:** inject interruption before/after blob publication, page checkpoint, journal compaction, summary update and schema creation; reopen with exact receipts and no duplicate external action. Test coherent backup/restore of database plus blobs. A process kill is not a power-loss test.
- **Delivery:** exercise clean new-profile creation and refusal of every pre-reset schema on the candidate engine, then native GUI/CLI, configured relocated packages and required Mac/Windows/Linux CI. Retain the old package as a code rollback reference; no current-profile data backup or migration is required by D091. Do not point an old engine at the new baseline profile. Update Core/Search/Gmail/Calendar/Quality contracts, phase plan and status when implementation evidence supports each change.

## Not included by this proposal

No real-profile reset until the replacement build passes its cutover checks; no real provider write/send/invitation, new provider, automatic local mail expiry, changed backup policy or readiness claim follows from this plan. D092's explicit retention editor prunes local derived mail after its shortening warning; there is still no automatic expiry. Remaining optimizations can be accepted, rejected or deferred individually from their measured evidence.
